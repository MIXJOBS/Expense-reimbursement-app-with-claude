# Sprint 3 受け入れ条件（PO作成）

出典：経費精算アプリ プロダクトバックログ（PO管理のDoc）。内容を変えたいときはPOに相談すること。
順番：PBI 6（監査ログ）→ PBI 5（領収書）。領収書の操作も監査ログに残したいため、監査ログを先に作る。

## スプリント開始時の持ち越し

- [ ] 差し戻し理由は trim せず入力どおり保存する。500文字の判定は空白も1文字として数える（Sprint 2のテスト担当の質問への回答）

## PBI 6：監査ログ

- [ ] 次の操作を記録する：ログイン成功・失敗、ログアウト、ロール付与・剥奪、申請の作成・編集・削除・提出、承認・差し戻し、領収書のアップロード・閲覧URLの発行
- [ ] 記録する項目：誰が（操作者ID。ログイン失敗は入力されたメールアドレス）、いつ、何に（対象の種類とID）、何を（操作の種類）、結果（成功・失敗）、変更前後の値、IPアドレス
- [ ] パスワード・passwordHash・Cookie・セッショントークンは記録しない
- [ ] 状態を変える操作は、業務の更新と監査ログの記録を同じトランザクションで行う。記録に失敗したら業務の更新も失敗させる
- [ ] 監査ログは追記のみ。アプリから更新・削除するコードを書かない。さらにDBのトリガーで UPDATE と DELETE を拒否する
- [ ] 管理者だけが GET /admin/audit-logs で閲覧できる。それ以外のロールは403
- [ ] 一覧は { items, total, page, pageSize } で返し、1ページ50件。操作者・対象・期間で絞り込める

## PBI 5：領収書のアップロード

- [ ] 受け付ける形式は JPEG・PNG・PDF だけ。拡張子や Content-Type ではなく、ファイルの中身（先頭のバイト）で判定し、それ以外は400
- [ ] 1ファイル5MBまで、1申請につき5枚まで。超えたら400
- [ ] アップロードできるのは申請者本人だけで、申請が「下書き」か「差し戻し」のときだけ。他人の申請は404、それ以外の状態は409
- [ ] 保存先は外から直接見えない場所にする。保存するファイル名はサーバーがUUIDで付け、元のファイル名は表示用にだけ保存する（保存パスに使わない）
- [ ] 閲覧は有効期限5分の署名付きURLで行う。URLを発行できるのは、申請者本人とその申請の承認者だけ。それ以外は404
- [ ] ダウンロード時は Content-Disposition: attachment と X-Content-Type-Options: nosniff を付ける
- [ ] 保存の仕組みは設計で提案すること（S3互換のMinIOをdocker composeで立てる案を推奨）

## PO判断：PBI 6設計への回答（2026-11-25）

対象：`.reports/2026-11-25-0827-backend-pbi6-design.md` の「判断が必要な点」

- 方式：Service内で業務の更新と同じトランザクションで記録する案を採用。CLAUDE.md横断ルール4の文言変更も承認（No.11）
- No.1 失敗の記録：ログイン失敗のみ。権限不足（403）の記録は宿題として後回し
- No.2 ロール付与：実際に作成されたときだけ記録
- No.3 ログイン失敗の理由：管理者向けログには区別して残してよい（レスポンスは今までどおり統一の401）
- No.4 絞り込み：actorEmail の完全一致での絞り込みも追加する（特定のメールアドレスへの攻撃を調べるため）
- No.5 閲覧の記録：申請の閲覧・監査ログの閲覧は記録しない。監査ログの閲覧の記録は宿題
- No.6 メール欄へのパスワード混入：メール形式の入力だけを記録するので、残りのリスクは受容
- No.7 期間：ISO8601の日時で、タイムゾーンのオフセット必須の半開区間（from以上・to未満）。日付への変換はフロントで行う
- No.8 保持期間：当面なし。宿題
- No.9 TRUNCATEの拒否：採用
- No.10 action・resultの絞り込み：追加しない
- No.12 署名付きURL・保存パス・保存ファイル名：監査ログに載せない。署名付きURLは「持っている人が見られる鍵」なので、ログに残すと閲覧権限が漏れるのと同じ
- No.13 持ち越し（差し戻し理由をtrimしない）：満たしているので完了
- No.14 レート制限（429）で弾かれた試行：監査ログには記録しない。宿題

## PO判断：PBI 6テストと設計の残りへの回答（2026-11-25）

対象：`.reports/2026-11-25-1220-test-pbi6-e2e.md`、`.reports/2026-11-25-1125-backend-pbi6-design-po.md`

- 並列実行での干渉：e2eは直列実行にする（jest-e2e.json に `maxWorkers: 1`）。e2eは同じテスト用DBを共有しており、「管理者の人数」のようなDB全体のルールを試すテストは並列では前提が崩れるため。担当はtest-agent
- sharedの古いビルド：`pretest:e2e` の最初に `@expense/shared` のビルドを入れ、毎回最新の型でテストが動くようにする。担当はbackend-engineer
- 記録の失敗で業務も失敗すること：e2eではなく、Serviceの単体テスト（recordをモックして例外を投げさせる）で確認する
- ロール再付与の応答コード：今の実装どおり201のまま。設計書の「204」を直す
- actorEmailの大文字小文字：今回はバイト一致のまま。メールアドレスを保存時・ログイン時に小文字にそろえる件は宿題
- from・toの形式：オフセットがあれば、秒なし・ミリ秒ありも受け付けてよい
- 8KB上限：申請の内容は200文字、差し戻し理由は500文字までなので超えない。今回はテスト不要
- 領収書の元のファイル名を監査ログに載せるか：PBI 5の設計で決める
